# 开发执行规则

## 一 Codex 的开发方式

### 每次只完成一个可验证的任务
Codex 先读项目约束和当前状态，检查现有工程，再选择依赖已经通过的最小任务。实现后运行与本次变更直接相关的检查，修复失败，记录证据和下一步。已有授权范围内的普通开发不需要逐项确认。[O1]

任务可以跨多次对话完成，但每次结束必须写清实际做到哪里。不同对话的接续依靠仓库文件，不能只依靠聊天记忆。AGENTS.md 保存稳定约束，STATUS.md 保存进度，DECISIONS.md 保存取舍。[O2]

### 文件分工
| 文件 | 用途 |
| --- | --- |
| AGENTS.md | Codex 每次开工需要遵守的项目规则 |
| docs/PRD.md | 产品行为与范围 |
| docs/ARCHITECTURE.md | 模块职责 数据契约 物理顺序 |
| docs/PLAN.md | 里程碑和任务依赖 |
| tasks/T001 至 T018 | 单项任务 交付物 检查与边界 |
| docs/STATUS.md | 当前任务 真实完成度 阻塞和接续点 |
| docs/ACCEPTANCE.md | 必须通过的运行与手感验收 |
| docs/PROMPTS.md | 开工 接续 修复和评审提示词 |

### Codex 和人的分工
Codex 编写 TypeScript、配置、校验器和测试，组织工程、构建、性能排查与交付记录。首次创建工程和资源导入优先使用锁定版本的 Cocos 编辑器生成合法文件；能通过已有工具完成时由 Codex 操作。

需要人工操作时，只列出具体入口、动作和预期结果，例如“用 3.8.x 打开工程，等待导入后运行 PhysicsLab”。没有编辑器、WebGL 或真机时，完成独立的代码与静态检查，并把运行验收标为阻塞，不能写成通过。

自动化检查验证规则和稳定性；物理爽感还需要实际画面与试玩判断。缺少后者时不得自动进入大量关卡和美术制作。

## 十四 仓库约束与接续规则

### AGENTS 的内容要短而稳定
根目录 AGENTS.md 固定产品方向、物理边界、完成标准和证据规则。具体调参、日志和临时失败放到配置或状态文件，避免稳定约束被大量过程文字覆盖。已有仓库规则先读再合并；本包文件不自动覆盖用户的现有规则。[O2]

### 每次实现的顺序
读 AGENTS.md、STATUS.md 和当前任务；检查相关源码与配置；写出简短执行计划；实现最小闭环；运行必要检查并修复；记录证据；更新任务状态和 STATUS.md。单任务涉及规则变更时同步 PRD、配置、验收和决策记录。

### 任务状态
NOT_STARTED 为未开始；IN_PROGRESS 为正在实现；CODE_READY 为代码完成但必要运行验证尚未通过；BLOCKED 为存在具体外部阻塞；DONE 为任务交付物与全部必要证据都齐备。不能为了推进里程碑把 CODE_READY 改成 DONE。

阻塞要写清缺什么、已经完成什么、最小解除动作和可独立继续的任务。运行受阻时可以完善纯逻辑和工具；不能把尚未跑过的核心物理当成通过，继续扩充成几十关。

### 变更和提交
保留用户已有改动，不执行清理全部未跟踪文件、硬重置或强推。是否提交、推送和发布按用户当次授权执行；文档不会强制每项开发都等待许可。任务总结给出改动、验证和剩余问题，避免只报文件数。

### 新对话如何接上
从 STATUS.md 的 currentTask 开始，复查最近证据和任务依赖。若状态写完成但证据缺失，先补验收或纠正状态。用户修改产品方向时先更新 DECISIONS.md 与受影响任务，保留此前真正验证过且仍适用的内容。

本包的开发规范是项目建议，不要求修改 Codex 全局配置，不需要安装自定义技能，也不依赖多代理执行。
