# 开发计划

## 十五 里程碑与进入条件

### 先过手感关
M0 建立环境与输入；M1 建立物理角色与弹道；M2 完成分部位受击和装备掉落；G1 是物理手感验收；通过后才进入内容、美术和渠道。里程碑按依赖推进，不把日历日期当作通过证明。

| 阶段 | 任务 | 交付与进入下一阶段的条件 |
| --- | --- | --- |
| M0 工程基线 | T001 T002 | 工程可打开 单位标定 输入取消正确 |
| M1 物理射击 | T003 T004 T005 | 能站立 倒地仍可瞄准 箭路可信 |
| M2 命中后果 | T006 T007 | 命中部位有差异 掉弓掉盔不重复 |
| G1 手感验收 | T008 | 实际试玩和对照录像通过 |
| M3 可玩内容 | T009 T010 T011 | 三关 胜败 三箭可从新档体验 |
| M4 表现与存档 | T012 T013 | 分层素材完整 结果和解锁可靠 |
| M5 性能与渠道 | T014 T015 T016 | 基线设备稳定 渠道预览可运行 |
| M6 交付 | T017 T018 | 必测用例通过 工程构建说明齐备 |

### G1 的必要内容
同一试验关里，录到箭飞行后击中头、腰、持弓臂、膝，看到不同受力；至少一次敌人掉弓、掉盔、跌台；玩家倒地后仍可操作。关闭命中粒子和伤害数字后，以上动作仍可辨认。

静态代码审查只能证明逻辑路径存在。G1 必须记录试玩结论和仍需调整的参数，由产品负责人确认手感方向；这是手感判断的必要输入，正常代码修复不因此重复询问确认。

### 失败时如何处理
穿透先查单位、步长、扫掠和去重；关节抖动先查锚点、质量和驱动力；看不清受击先查人物比例和控制恢复，再调特效。G1 不通过时保持 M3 至 M6 的实现范围冻结，只做能帮助定位问题的独立工作。

## 二十三 排期风险与交付

### 排期按验证门槛复估
共 40 程序人日加 5 人日缓冲，约 9 个工作周；另需原创美术切片与音效配合。Codex 可以减少编码与文档整理时间，但物理调参、设备兼容和手感试玩仍需要实际迭代，不能直接按倍数压缩工期。

T001 至 T008 合计 19 程序人日。完成 G1 后，根据真实碰撞稳定性、手感和素材质量复估后续任务。若由同一人承担全部美术，另留约 10 至 15 人日；首领和渠道接入不确定性使用缓冲或单独变更单处理。

| 风险信号 | 优先处理 |
| --- | --- |
| 关节分离 高频抖动 | 检查单位 锚点 质量比 驱动限幅 |
| 飞得远但角色难辨认 | 调构图 射距与相机 保留身体比例 |
| 命中只平移 | 接触点冲量 局部回正权重 支撑腿 |
| 箭漏碰或重复扣血 | 连续碰撞 扫掠 路径排序 去重 |
| 重开后越来越卡 | 刚体关节释放 对象池 监听器 |
| 渠道构建方式不匹配 | 单独验证最小包 不直接重写战斗 |

### 最终交接清单
完整 Cocos 工程及 meta；锁定版本和工具说明；可追溯素材；配置及迁移版本；所选渠道构建；源码版本与构建清单；必要用例结果和录屏；已知问题及重现方法。

每个构建记录应用版本、引擎小版本、源码标识、配置哈希、渠道、构建时间和运行入口。工程交付前从干净副本重新打开并构建，避免依赖某台机器的未提交缓存。

### 本资料包交付检查
文档、任务依赖、关卡引用、质量比例和配置种子做静态一致性检查；Word 渲染检查可读性。游戏规则测试、运行、性能和渠道真机验证在后续开发任务执行，当前均未执行。

所有任务卡保留未开始状态。开工后由 Codex 将实际证据写回状态文件，不能因为本计划足够详细就视为游戏已完成。
